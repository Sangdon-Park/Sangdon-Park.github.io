# 게시글 클릭 기록과 목록 정렬

대전대학교 컴퓨터공학과 박상돈 / 취창업역량강화 수업용 모의 지원 프로젝트

## 프로젝트 개요

클릭 한 번이 서버에 저장되고 다음 목록에 반영되는 과정을 구현한 로컬 프로그램입니다.
예제 제작·검증일은 2026.09.06입니다. 개인 프로젝트를 수행하는 모의 지원자 역할로 서버 API, DB, 시연 화면, 테스트, 조회 실험 전체를 설명합니다. 실제 학생의 수행 이력이나 실무 경력을 의미하지 않습니다.

사용자가 전공책을 선택하면 기록을 저장하고 책 게시글을 먼저 보여줍니다. 게시글 6개는 합성 데이터입니다. 로그인, 판매글 작성·수정·삭제, 채팅, 인터넷 공개 운영은 현재 구현 범위에 없습니다.

## 검토할 핵심 내용

1. **담당 범위**: 요청 검사와 응답은 app.py, 저장·조회는 store.py, 클릭 전송과 화면 갱신은 web/app.js에 있습니다.
2. **중복 저장 문제**: 같은 요청 번호가 다시 오면 저장한 내용과 비교합니다. 원본과 사용자 요약은 한 트랜잭션에 묶습니다.
3. **선택 이유**: 화면 버튼 잠금은 재전송을 보장하지 못하고 메모리의 번호는 서버 재시작 시 사라집니다. SQLite 파일에 고유 번호를 남겨 재접속 뒤에도 판단합니다. 동시 쓰기가 직렬화되는 한계도 있습니다.
4. **검증 결과**: 동일 요청 재전송, 내용 충돌, 오류 주입, 동시 전달 등 12개 테스트를 통과했습니다.
5. **조회 실험**: 동일 SQL의 인덱스 전후 결과와 시간을 비교했습니다. 수치와 조건은 아래와 evidence/ 원본에 있습니다.

## 실행 방법

Python 3.12에서 확인했습니다. ZIP을 풀고 campus-feed 폴더에서 실행합니다.

```powershell
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
./.venv/Scripts/python.exe -m uvicorn app:app --host 127.0.0.1 --port 8770
```

브라우저에서 http://127.0.0.1:8770 을 엽니다. API 문서는 /docs 입니다.
macOS/Linux는 실행 파일 경로를 ./.venv/bin/python으로 바꿉니다.
이미 같은 포트에서 서버가 실행 중이면 그 화면을 열거나 빈 포트로 실행합니다.

## 시연 순서와 예상 결과

1. 기록이 없는 상태에는 키보드와 스탠드가 목록 앞에 나옵니다.
2. 알고리즘 교재를 선택합니다. 오른쪽에 전공책 클릭 1건이 보이고, 목록 앞에는 알고리즘·데이터베이스 교재가 옵니다.
3. '같은 요청이 다시 도착하면?'을 열고 '방금 클릭한 요청을 다시 보내기'를 누릅니다. 기록은 1건으로 유지됩니다.
4. 새로고침합니다. DB 파일에 저장한 기록은 남습니다.

사용자가 실제로 다시 클릭하면 새 요청 번호를 붙입니다. 모든 반복 클릭을 무시하는 기능이 아닙니다.
화면의 student-demo는 학습용 사용자 구분값입니다. 본인 인증이나 접근 권한 검사가 없습니다.

완전히 새로운 시연은 서버를 종료한 뒤, 아직 사용하지 않은 DB 경로로 실행합니다.

```powershell
$env:CAMPUS_FEED_DB = '.runtime/new-demo.db'
./.venv/Scripts/python.exe -m uvicorn app:app --host 127.0.0.1 --port 8770
```

## 코드와 포트폴리오의 연결

| 포트폴리오 | 근거 |
| --- | --- |
| 1~2쪽: 개요·담당 구현 | app.py, store.py, web/ |
| 3쪽: 중복 저장 문제 | Store.ingest, 중복·충돌·오류 주입·동시 요청 테스트 |
| 4쪽: 조회 실험 | benchmark.py, evidence/benchmark.json, latency.csv |
| 5~6쪽: 검사·한계·재현 | test_app.py, evidence/verification.json, tests.txt, 이 README |

목록은 카테고리별 클릭 횟수로 정렬하며 기록이 없으면 최신순입니다. 점수가 같으면 합성 게시글 생성 순서로 정합니다. 모델 학습이나 추천 정확도 실험은 없습니다.

## 테스트 재현

별도 터미널의 같은 폴더에서 실행합니다.

```powershell
./.venv/Scripts/python.exe verify.py
```

12개 테스트의 원본 코드는 test_app.py, 실행 결과는 evidence/verification.json, tests.txt, tests.xml입니다.
같은 요청을 8개 스레드에서 16회 전달할 때 1회만 수락하는지 검사합니다. 저장 중 오류를 주입하면 원본과 요약 모두 되돌아가는지도 검사합니다.
사용자별 데이터 분리는 로그인·권한 검사의 증거가 아닙니다. 의존성의 폐기 예정 기능 경고 2건은 원본 로그에 남아 있습니다.

## DB 조회 실험

```powershell
./.venv/Scripts/python.exe benchmark.py
```

이 명령은 성능 결과 파일을 갱신합니다. 재실행한 수치는 장비와 상태에 따라 달라집니다.

동봉한 결과는 합성 이벤트 100,000건, 사용자 1,000명, seed 20260906으로 측정했습니다.
조건당 300회씩 3회차, 회차·조건마다 워밍업 30회입니다.
실행 순서는 기준→인덱스 / 인덱스→기준 / 기준→인덱스입니다.
한 프로세스·한 연결에서 SQL 실행과 결과 읽기만 순차 측정했습니다.

- 통합 p95: 인덱스 없음 5.3043ms, 있음 0.0866ms.
- 회차별 p95: 기준 4.3541 / 4.6296 / 6.4508ms, 인덱스 0.0843 / 0.0823 / 0.0901ms.
- 원본 측정값은 latency.csv 1,800행입니다. 모든 조회 결과는 같고 SQL 오류는 없었습니다.
- 인덱스 추가 공간은 약 3.20MiB입니다.
- 환경: Windows 11, Intel Core Ultra 9 285K, 논리 CPU 24개, Python 3.12.14, SQLite 3.53.1.
- HTTP 전체 응답, 네트워크, 동시 접속 부하, 쓰기 비용은 측정하지 않았습니다.
